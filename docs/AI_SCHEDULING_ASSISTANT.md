# CalTalk AI 일정 비서 최우선 설계

## 문서의 지위

이 문서는 CalTalk의 현재 최우선 제품 과제와 구현 경계를 정의한다. 카카오톡에서 자유로운 한국어 대화로 일정을 조회·등록·수정할 수 있는 기능이 완성되기 전까지, 기능과 무관한 UI/UX 미세 조정보다 이 문서의 작업을 우선한다.

## 제품 목표

연결된 사용자가 카카오톡에서 평소 사용하는 문장으로 다음 작업을 수행할 수 있어야 한다.

- 일정과 여유 시간을 질문한다.
- 새 일정을 등록한다.
- 기존 일정을 수정한다.
- 필요한 경우 일정을 삭제한다.
- 정보가 부족하면 자연스러운 추가 질문을 받는다.
- 후보가 여러 개면 안전하게 선택한다.
- 충돌하거나 상태를 변경하는 작업은 적용 전에 내용을 확인한다.

정해진 몇 개의 발화 패턴만 매칭하는 기능은 이 목표를 충족하지 않는다.

## 확정 아키텍처

```text
카카오톡 사용자
  -> 카카오 챗봇 스킬
  -> CalTalk 인증·사용자 연결 확인
  -> 백엔드 기본 규칙 검사
  -> Ollama 로컬 모델 1차 구조화
  -> 백엔드 스키마·도메인 검증
       |-- 명확하고 완전함: 조회 또는 확인 단계 진행
       |-- 필수 정보 부족: 사용자에게 재질문
       |-- 후보가 여러 개: 후보를 제시하고 선택 요청
       `-- 정보는 충분하지만 해석 실패/복잡: 선택적 OpenAI fallback
  -> 백엔드가 권한·시간대·충돌·버전 재검증
  -> 카카오톡 응답
```

## AI 제공자 정책

### 기본 제공자

- Ollama를 기본 제공자로 사용한다.
- 1차 후보 모델은 현재 개발 PC의 RTX 5060 8GB에서 실행 가능한 Qwen3 8B 계열 양자화 모델이다.
- 모델은 교체 가능해야 하며 비즈니스 로직이 Ollama HTTP 형식에 종속되면 안 된다.

### 선택적 fallback

- OpenAI는 필수 의존성이 아니라 선택적 fallback이다.
- OpenAI API 키가 없어도 Ollama와 재질문 흐름으로 서비스가 동작해야 한다.
- OpenAI에는 해석에 필요한 최소 정보만 전달한다.
- OpenAI 장애·한도 초과·비활성 상태에서는 안전하게 재질문으로 전환한다.

### 제공자 추상화

```text
NaturalLanguageProvider
  |- OllamaProvider       (기본)
  `- OpenAiProvider       (선택)
```

제공자 출력은 동일한 버전 관리된 명령 스키마로 변환한다.

## 라우팅 원칙

OpenAI fallback 여부를 모델이 출력한 confidence 하나로 결정하지 않는다. 다음 신호를 백엔드가 함께 검사한다.

- JSON 또는 구조화 출력 스키마 검증 실패
- 지원 의도를 하나로 확정하지 못함
- 날짜·시간 해석 결과가 유효하지 않음
- 발화에는 충분한 정보가 있지만 로컬 모델이 필드를 추출하지 못함
- 복합 조건이나 대화 맥락을 로컬 모델이 일관되게 처리하지 못함
- 모델 결과와 DB 후보 또는 도메인 규칙이 충돌함

다음 상황은 OpenAI로 보내지 않고 사용자에게 질문한다.

- 필수 날짜·시간·일정 대상이 발화에 없음
- 같은 이름의 일정이 여러 개라 선택이 필요함
- 사용자의 선호나 의도를 알 수 없어 정답이 존재하지 않음
- 삭제 또는 큰 변경의 최종 동의가 필요함

## 모델 출력 계약

모델은 자연어 답변 대신 우선 구조화된 명령 후보를 생성한다. 예시는 다음과 같다.

```json
{
  "schemaVersion": "1.0",
  "intent": "UPDATE_EVENT",
  "status": "READY",
  "title": "팀 미팅",
  "startAtLocal": "2026-08-05T15:00:00",
  "timezone": "Asia/Seoul",
  "missingFields": [],
  "ambiguities": [],
  "userFacingQuestion": null
}
```

허용 의도는 최소 `SEARCH_EVENTS`, `CREATE_EVENT`, `UPDATE_EVENT`, `DELETE_EVENT`, `FREE_TIME_QUERY`, `UNKNOWN`으로 관리한다. 스키마에 없는 필드, 잘못된 시간, 존재하지 않는 일정 ID, 다른 사용자 소유 일정은 백엔드가 거부한다.

## 실행 안전성

- AI는 DB에 직접 접근하지 않는다.
- 사용자 식별과 일정 소유권은 연결된 카카오 사용자 HMAC과 서버 DB로만 판단한다.
- 조회는 검증 후 즉시 응답할 수 있다.
- 생성·수정·삭제는 후보를 만든 뒤 백엔드 confirmation을 거친다.
- 일정 충돌, 최신 버전, 시간대 변환은 기존 CalTalk 도메인 서비스를 재사용한다.
- 중복 카카오 요청이 같은 변경을 두 번 실행하지 않도록 idempotency를 적용한다.
- 모델 프롬프트나 응답에 포함된 지시가 보안·권한 규칙을 변경할 수 없다.

## 개인정보와 로그

- API 키, 연결 코드, 카카오 사용자 원문 ID를 기록하지 않는다.
- 운영 로그에 전체 발화와 전체 일정 내용을 기본 저장하지 않는다.
- 진단에는 요청 ID, 제공자, 처리 시간, 명령 종류, 검증 결과, fallback 사유처럼 최소한의 메타데이터를 사용한다.
- OpenAI fallback에는 요청 해결에 필요한 최소 일정 후보만 전달한다.

## 응답 시간

카카오 스킬의 짧은 응답 제한을 고려한다.

- Ollama 모델을 미리 로딩하고 유지한다.
- 로컬 분석에 명시적인 제한 시간을 둔다.
- 순차 fallback이 제한 시간을 넘길 가능성이 있으면 카카오 Callback API를 사용한다.
- Callback을 사용할 수 없는 환경에서는 무리하게 기다리지 않고 안전한 재질문을 반환한다.

## 구현 순서

1. Ollama 설치와 Qwen3 8B 실행 성능 측정
2. `NaturalLanguageProvider`와 버전 관리 명령 스키마 구현
3. Ollama 구조화 분석 및 백엔드 검증기 구현
4. 일정 조회와 여유 시간 질문 연결
5. 다회차 재질문·후보 선택 상태 구현
6. 생성·수정·삭제 confirmation 연결
7. 선택적 OpenAI fallback과 회로 차단 구현
8. 실제 카카오톡 E2E 및 대표 발화 평가
9. 관측성·속도 제한·운영 배포 보강
10. 핵심 기능 완료 후 UI/UX 고도화

## 완료 기준

다음 조건을 모두 충족해야 최우선 과제가 해결된 것으로 본다.

- 실제 카카오톡 채널에서 연결된 사용자만 자신의 일정을 다룬다.
- 다양한 한국어 표현으로 조회·등록·수정이 가능하다.
- 정보 부족과 다중 후보를 추측하지 않고 대화로 해결한다.
- 생성·수정·삭제와 충돌 일정은 확인 없이 반영되지 않는다.
- Ollama만으로 기본 서비스가 동작한다.
- OpenAI fallback은 선택적으로 켜고 끌 수 있으며 장애 시 안전하게 복구한다.
- 중복 요청, 만료된 확인, 다른 사용자 일정 접근을 차단한다.
- 대표 발화 평가와 백엔드·프론트·카카오 E2E 테스트가 통과한다.

예외이며, 모델 출력 검증·권한·확인·일정 실행 책임은 계속 CalTalk 백엔드가 가진다.

### 2026-08-04 로컬 모델 검증 결과

- Ollama `0.32.5`, `qwen3:8b` 설치 완료
- RTX 5060 8GB에서 모델 100% GPU 적재 확인
- 최초 모델 적재 요청 약 47초, 워밍업 후 한국어 구조화 요청 약 1.5~3.6초
- 생성·조회·수정 모호성·빈 시간 조회 의도 분류 확인
- 모델 결과를 그대로 신뢰하지 않고 `ScheduleCommandValidator`가 필수 필드와 재질문 상태를 재검증
- 다음 단계: 상대 날짜/시간을 확정 시각으로 변환하는 결정론적 해석기와 일정 조회 연결
- 사용자 시간대 기준 `오늘`, `내일`, `모레`, 이번/다음 주 요일, ISO 날짜, `M월 d일` 조회 연결 완료
- 카카오톡 조회 응답은 최대 5개 일정을 시간순으로 표시하며 데이터 변경은 수행하지 않음
- 카카오 응답 지연을 피하기 위해 Ollama 모델을 `keep_alive=-1`로 GPU 메모리에 유지
- 실제 연결 계정으로 `내일 일정 알려줘` 발화가 2026-08-05 일정 조회 결과를 반환하는 것 확인
- 일정 생성 초안은 Redis에 10분간만 저장하며, 외부 카카오 사용자 ID 대신 HMAC 키를 사용
- 제목·날짜·시작·종료 시간이 모두 있어야 생성 확인을 제시하고 사용자의 `확인` 전에는 DB를 변경하지 않음
- 확인 직전 기존 일정 충돌을 다시 검사하며 충돌 시 생성하지 않음
- 생성 변경 이력의 source channel을 `KAKAO`로 기록
- 연결 사용자 조회 시 `user`를 EntityGraph로 함께 로딩해 웹훅 트랜잭션 밖의 LazyInitialization 오류를 방지
- 카카오 생성·삭제 실채널 E2E와 DB/Redis 정리 검증 완료
- 삭제·수정 후보는 서버가 소유권과 현재 버전을 확인해 Redis에 10분만 유지
- 같은 날짜의 일정 시간 수정은 확인 직전 버전과 충돌을 다시 검사하며 이력 source를 `KAKAO`로 기록
- 실제 수정 E2E에서 15:00~16:00 일정이 17:00~18:00으로 변경되고 버전 1 및 `KAKAO / UPDATE` 이력 확인
- 실제 빈 시간 E2E에서 17:00~18:00 일정을 제외한 09:00~17:00 구간 반환 확인
- OpenAI Responses API 기반 구조화 fallback 구현 완료 (`gpt-5.6-sol`)
- Ollama 결과가 `UNKNOWN` 또는 `UNSUPPORTED`이거나 로컬 호출이 실패한 경우에만 fallback 사용
- 정보가 부족한 `NEEDS_CLARIFICATION`은 OpenAI를 호출하지 않고 사용자에게 재질문
- Redis 시간당 호출 상한 기본 20회와 8초 timeout 적용; 한도·장애 시 로컬 결과로 안전 복귀
- OpenAI 키와 모델의 실제 API 호출 성공 및 전체 백엔드 테스트 122개 통과
- Ollama 중단 상태의 실제 카카오톡 E2E에서 OpenAI fallback 사용과 약 3.3초 응답 확인
- fallback이 상대 시간 표현을 `모레 10:45~12:15`로 구조화하고 확인 단계까지 정상 진입
- 수정·삭제 대상이 여러 개인 경우 최대 5개 후보를 시간순으로 제시하는 선택 대화 구현
- `2`, `2번`, `두 번째`, `오후 일정`, `15:00` 형태의 후속 선택 지원
- 후보 선택 상태는 Redis에 10분간 보관하고 최종 확인 시 ID·버전을 다시 검증
- 복수 후보 선택 회귀 테스트를 포함한 전체 백엔드 테스트 126개 통과
- 실제 카카오톡 E2E에서 동일 제목의 10:00·15:30 일정 후보 표시와 `오전 일정` 선택 확인
- 선택된 10:00 테스트 일정만 삭제되고 15:30 기존 일정이 유지되는 DB 검증 완료
- Kakao 동기 스킬은 5초 제한이 있어 Ollama 지연 후 순차 fallback은 응답 유실 가능; Callback API 적용 필요
- Kakao Callback API 백엔드 구현 완료: 즉시 `useCallback=true` 승인 후 가상 스레드에서 최종 응답 전송
- callback URL은 HTTPS `kakao.com` 하위 도메인만 허용하고 10초 전송 timeout 및 1회 전송 적용
- callback 컨트롤러·URL 보안·최종 POST 테스트를 포함한 전체 백엔드 테스트 129개 통과
- 실제 카카오톡 E2E에서 `폴백 블록`의 Callback 활성화 후 대기 메시지와 최종 일정 응답이 순서대로 전달되는 것 확인
- Callback은 봇 전체 설정이 아니라 스킬을 호출하는 블록별 설정이므로, 자유 발화를 받는 폴백 블록을 포함한 모든 스킬 진입 블록에서 활성화해야 함
- UX 개선: 모든 요청은 최대 2.5초 동안 직접 응답을 우선 시도하고, 이 시간 안에 완료되지 않은 요청만 Callback으로 전환해 대기 메시지를 표시함. `확인`·`취소`·후보 번호/시간 선택은 즉시 동기 처리함
