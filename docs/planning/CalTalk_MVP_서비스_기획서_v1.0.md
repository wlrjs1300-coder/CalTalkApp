# CalTalk MVP 서비스 기획서 최종본

- 문서 버전: 1.0 Final
- 확정일: 2026-07-25
- 프로젝트 유형: 개인 풀스택 포트폴리오
- 서비스 형태: PWA 기반 개인 캘린더 + 카카오톡 채널 챗봇
- 기준 시간대: `Asia/Seoul`

---

## 1. 프로젝트 개요

### 1.1 서비스명

**CalTalk**

### 1.2 서비스 정의

CalTalk는 사용자가 PWA 캘린더와 카카오톡 채널 챗봇에서 자연어로 개인 일정을 조회·등록·수정할 수 있도록 하는 대화형 일정 관리 서비스다.

PWA는 서비스의 본체이며, 사용자는 웹 화면에서 일정을 직접 관리할 수 있다. 카카오톡 채널 챗봇은 사용자가 캘린더 화면을 열지 않고도 일정에 접근할 수 있도록 돕는 보조 인터페이스다.

### 1.3 한 문장 소개

> CalTalk는 카카오톡과 웹에서 자연어로 개인 일정을 안전하게 조회·등록·수정할 수 있는 PWA 기반 AI 캘린더 서비스다.

### 1.4 핵심 설계 원칙

1. PWA는 카카오톡 연동 없이도 독립적으로 동작한다.
2. LLM은 사용자 문장을 제한된 일정 명령으로 구조화한다.
3. LLM은 DB에 직접 접근하거나 SQL을 생성·실행하지 않는다.
4. 실제 조회와 변경은 백엔드가 인증·권한·입력값을 검증한 뒤 처리한다.
5. 자연어를 통한 일정 생성·수정은 사용자 최종 확인 전에는 실행하지 않는다.
6. 날짜·시간·대상 일정이 모호하면 추측하지 않고 재질문한다.
7. 외부 서비스 장애가 발생해도 이미 저장된 일정은 PWA에서 관리할 수 있어야 한다.

---

## 2. 프로젝트 배경

기존 캘린더는 기능이 충분하지만 모바일에서 짧은 일정을 등록하거나 기존 일정의 시간을 바꾸려면 앱 실행, 날짜 이동, 입력 필드 선택 등 여러 단계를 거쳐야 한다.

CalTalk는 사용자가 자주 사용하는 카카오톡과 대화형 웹 인터페이스에서 자연어로 일정을 관리할 수 있게 하여 다음 문제를 줄이고자 한다.

- 특정 날짜의 일정을 확인하기 위해 캘린더 화면을 탐색해야 하는 불편
- 모바일에서 제목·날짜·시간을 각각 입력해야 하는 번거로움
- 수정할 일정을 찾아 상세 화면으로 이동해야 하는 복잡성
- 자연어 해석 오류로 잘못된 일정이 저장될 수 있는 위험

---

## 3. 서비스 목표

CalTalk MVP의 목표는 다음과 같다.

1. 사용자가 PWA에서 본인의 개인 일정을 직접 조회·등록·수정·삭제할 수 있게 한다.
2. 사용자가 웹 대화 화면에서 자연어로 일정을 조회·등록·수정할 수 있게 한다.
3. 사용자가 카카오톡 채널 챗봇에서 자연어로 일정을 조회·등록·수정할 수 있게 한다.
4. 카카오 챗봇 사용자와 CalTalk 사용자를 안전한 일회용 절차로 연결한다.
5. 일정 생성·수정의 오실행, 중복 실행, 다른 사용자 일정 접근을 방지한다.
6. 카카오톡 또는 LLM 연동 장애 시에도 PWA의 직접 일정 관리 기능을 제공한다.
7. 인증·검증·예외 처리·테스트·배포까지 포함한 실제 서비스형 포트폴리오를 완성한다.

## 4. 핵심 사용자

### 4.1 주요 사용자

**개인 일정 관리가 필요한 일반 사용자**

### 4.2 대표 사용자 예시

- 팀 단위 공유 캘린더 사용자

| 공통 원칙 | 채널별 어댑터와 공통 일정 도메인 로직 분리 |

## 6. 핵심 용어

### 6.1 CalTalk 사용자

PWA에서 회원가입하고 본인의 일정 데이터를 소유하는 내부 사용자다.

### 6.2 카카오 챗봇 사용자 식별값

카카오 챗봇 스킬 요청에 포함되는 봇별 사용자 식별값이다. 내부 사용자 ID와 직접 동일하게 사용하지 않는다.

### 6.3 카카오 챗봇 사용자 연결

CalTalk 사용자와 카카오 챗봇 사용자 식별값을 연결하는 절차다. 카카오 로그인이나 카카오 계정 통합을 의미하지 않는다.

### 6.4 일정 후보

자연어를 해석했지만 아직 DB에 반영되지 않은 생성 또는 수정 예정 데이터다.

### 6.5 대기 명령

추가 정보, 대상 선택 또는 최종 확인을 기다리는 일시적인 대화 상태다.

### 6.6 변경 이력

일정 생성·수정·삭제의 주체, 시각, 변경 전후 핵심 값을 기록하는 내부 감사 데이터다. MVP에서는 별도의 사용자용 이력 화면을 필수로 제공하지 않는다.

## 7. MVP 구현 단계

### 7.1 사전 기술검증

- 카카오비즈니스 및 챗봇 관리자센터 접근 가능 여부 확인
- 카카오톡 채널과 테스트 봇 생성 가능 여부 확인
- 공중망 HTTPS 스킬 서버 호출 가능 여부 확인
- 카카오 스킬 요청·응답 JSON 검증
- 사용자 식별값 확인
- 5초 응답 제한 대응 가능성 확인

### 7.2 MVP-1: PWA 기본 캘린더

- 회원가입
- 로그인
- 로그아웃
- 사용자 시간대
- 월간 캘린더
- 날짜별 일정 목록
- 일정 상세
- 일정 직접 등록·수정·삭제
- PWA 설치 가능 상태

### 7.3 MVP-2: 웹 자연어 일정 관리

- 특정 하루의 일정 조회
- 일정 등록 요청 해석
- 일정 수정 요청 해석
- 필수값 재질문
- 수정 대상 검색·선택
- 충돌 안내
- 최종 확인
- 중복 실행 방지

### 7.4 MVP-3: 카카오톡 연동

- 카카오 챗봇 사용자 연결·해제
- 연결되지 않은 사용자 안내
- 카카오톡 일정 조회
- 카카오톡 일정 등록
- 카카오톡 일정 수정
- PWA 일정 상세 화면 연결

### 7.5 MVP-4: 안정화와 배포

- 권한 검증
- 입력값 검증
- 요청 제한
- 예외·장애 처리
- 자동 테스트
- 주요 흐름 수동 검증
- 회원 탈퇴 및 본인 데이터 삭제
- 프론트엔드·백엔드 배포

## 9. 핵심 사용자 시나리오

### 9.1 PWA 직접 일정 관리

1. 사용자가 회원가입 또는 로그인한다.
2. 월간 캘린더에서 날짜를 선택한다.
3. 일정 목록과 상세 내용을 확인한다.
4. 폼에서 일정을 등록하거나 수정한다.
5. 본인의 일정을 삭제할 수 있다.
6. 직접 입력 폼의 저장 버튼은 사용자의 명시적 실행으로 간주한다.

### 9.2 웹 자연어 일정 등록

1. 사용자가 “내일 오후 2시에 치과 일정 추가해줘”라고 입력한다.
2. LLM이 명령·제목·날짜·시간을 구조화한다.
3. 백엔드가 필수값과 날짜·시간을 검증한다.
4. 종료 시간이 없으면 1시간 뒤로 설정한다.
5. 기존 일정과의 충돌을 검사한다.
6. 절대 날짜와 시간을 포함한 일정 후보를 보여준다.
7. 사용자가 승인하면 한 번만 저장한다.

### 9.3 카카오 챗봇 사용자 연결

1. 사용자가 PWA에 로그인한다.
2. PWA에서 짧은 유효시간을 가진 일회용 연결 코드를 발급받는다.
3. 사용자가 카카오톡 채널 챗봇에 연결 코드를 입력한다.
4. 서버가 코드의 유효성·사용 여부·시도 횟수를 검증한다.
5. CalTalk 사용자와 해당 봇의 사용자 식별값을 1:1로 연결한다.
6. 연결이 완료되면 기존 대기 명령은 폐기하고 새 요청부터 처리한다.

### 9.4 카카오톡 일정 조회

1. 사용자가 “내일 일정 알려줘”라고 입력한다.
2. 서버가 챗봇 사용자 연결 상태를 확인한다.
3. LLM이 조회 명령과 날짜를 구조화한다.
4. 백엔드가 연결된 사용자의 일정만 조회한다.
5. 시간순으로 일정 목록을 반환한다.
6. 일정이 없으면 빈 상태 안내를 반환한다.

### 9.5 카카오톡 일정 수정

1. 사용자가 “내일 치과 일정을 오후 4시로 바꿔줘”라고 입력한다.
2. 백엔드가 본인 소유 일정 중 수정 후보를 찾는다.
3. 대상이 없으면 날짜나 제목을 다시 질문한다.
4. 대상이 여러 개면 사용자가 하나를 선택한다.
5. 변경하지 않은 필드는 기존 값을 유지한다.
6. 변경 전후 내용과 충돌 여부를 보여준다.
7. 사용자가 승인하면 대상과 권한을 다시 검증한 후 한 번만 수정한다.

## 10. 자연어 명령 범위

### 10.1 허용 명령

- `SEARCH_EVENTS`: 일정 조회
- `CREATE_EVENT`: 일정 등록 후보 생성
- `UPDATE_EVENT`: 일정 수정 후보 생성
- `UNKNOWN`: 지원하지 않거나 해석하기 어려운 요청

명령 이름은 기술 설계에서 변경할 수 있지만, 허용 목록 기반 검증 원칙은 유지한다.

### 10.2 MVP 조회 범위

카카오톡과 웹 자연어 조회는 다음 범위부터 지원한다.

- 오늘
- 내일
- 특정 날짜
- 상대 표현으로 지정된 특정 하루

다음 조회는 MVP 이후 확장 후보로 둔다.

- 이번 주 또는 다음 주 전체
- 임의의 날짜 구간
- 월간 자연어 요약
- 장소·키워드·복합 조건 검색

### 10.3 지원하지 않는 명령

- 자연어 일정 삭제
- 반복 일정 생성·수정
- 다른 사용자 일정 조회
- 팀·공유 일정 관리
- 사용자의 승인 없는 자동 일정 배치

## 11. 일정 입력 규칙

### 11.1 제목 누락

일정 제목을 다시 질문한다.

### 11.2 날짜 누락

일정 날짜를 다시 질문한다.

### 11.3 시작 시간 누락

시간을 임의로 추측하지 않고 반드시 다시 질문한다.

### 11.4 종료 시간 누락

새 일정 생성에서만 시작 시간 기준 1시간 뒤로 자동 설정한다.

예:

- 시작: 14:00
- 종료: 15:00

자동 설정된 종료 시간은 최종 확인에 표시한다.

### 11.5 장소 누락

장소 없이 등록할 수 있으며 확인 화면에는 `장소 없음`으로 표시한다.

### 11.6 종일 표현

MVP에서는 종일 일정을 지원하지 않는다. “생일”, “하루 종일”처럼 시작 시간이 없는 요청에는 시간을 다시 질문한다.

### 11.7 과거 일정

- 웹·카카오 자연어를 통한 과거 일정 생성과 과거 시각으로의 수정은 허용하지 않는다.
- PWA 직접 입력에서는 사용자가 절대 날짜를 명시적으로 선택하므로 과거 일정 등록·수정·삭제를 허용한다.
- PWA에서 과거 일정을 저장할 때는 선택한 절대 날짜와 시간을 저장 전에 명확히 표시한다.

### 11.8 종료 시간이 시작 시간보다 빠르거나 같은 경우

- 다음 날이라는 표현이 명확하지 않으면 재질문한다.
- “밤 11시부터 다음 날 오전 1시”처럼 날짜 경계가 명시되면 허용한다.
- 종료 시각은 항상 시작 시각보다 뒤여야 한다.

---

## 12. 날짜·시간 해석 규칙

1. 저장된 사용자 시간대를 기준으로 해석한다.
2. 신규 사용자의 기본 시간대는 `Asia/Seoul`이다.
3. 카카오 요청의 시간대는 보조 정보로 활용하되 계정의 저장 시간대를 최종 기준으로 사용한다.
4. “오늘”, “내일”, “다음 주 화요일”은 요청이 발생한 시각을 기준으로 절대 날짜로 변환한다.
5. 최종 확인에는 반드시 연·월·일·요일·시작·종료 시간을 표시한다.
6. 해석 가능한 날짜나 시간이 둘 이상이면 추측하지 않고 재질문한다.
7. 서버·DB·API의 저장 시간 형식은 기술 설계서에서 결정하되 사용자 시간대 변환 규칙을 테스트한다.

---

## 13. 일정 수정 규칙

### 13.1 부분 수정

사용자가 언급한 필드만 변경하고 나머지는 기존 값을 유지한다.

수정 가능 필드:

- 제목
- 날짜
- 시작 시간
- 종료 시간
- 장소

### 13.2 시작 시간만 변경

기존 일정의 지속 시간을 유지한다.

예:

- 변경 전: 14:00~15:30
- 요청: “오후 4시로 바꿔줘”
- 변경 후보: 16:00~17:30

### 13.3 날짜만 변경

기존 시작·종료 시간과 지속 시간을 유지한다.

### 13.4 종료 시간만 변경

기존 시작 시간을 유지하고 새 종료 시간이 시작 시간보다 뒤인지 검증한다.

### 13.5 장소 제거

“장소 지워줘”, “장소 없음으로 바꿔줘”처럼 의도가 명확한 경우 장소 값을 비울 수 있다.

### 13.6 수정 대상 없음

사용자에게 제목이나 날짜 조건을 다시 질문한다.

### 13.7 수정 대상 여러 개

후보의 제목과 절대 날짜·시간을 보여주고 사용자가 하나를 선택하도록 한다.

### 13.8 최종 재검증

승인 시점에 대상 일정의 존재 여부, 소유권, 현재 값, 충돌 여부를 다시 확인한다. 승인 대기 중 일정이 변경되었다면 새 후보를 다시 보여준다.

---

## 14. 일정 충돌 규칙

1. 새 일정 또는 수정된 일정의 시간 구간이 기존 일정과 일부라도 겹치면 충돌로 판단한다.
2. 충돌은 오류가 아니라 경고다.
3. 충돌 일정의 제목과 절대 시간을 보여준다.
4. 사용자는 다음 중 하나를 선택한다.
   - 그대로 등록 또는 변경
   - 다른 시간 입력
   - 취소
5. 사용자가 그대로 진행을 명시적으로 승인한 경우에만 겹치는 일정을 저장한다.
6. 본인 소유 일정만 충돌 검사 대상으로 사용한다.

## 15. 확인·만료·중복 실행 규칙

### 15.1 최종 확인

웹 대화와 카카오톡에서 일정 생성·수정은 최종 확인 전에는 DB를 변경하지 않는다.

생성 확인 항목:

- 제목
- 절대 날짜
- 시작 시간
- 종료 시간
- 장소
- 충돌 여부

수정 확인 항목:

- 대상 일정
- 변경 전 값
- 변경 후 값
- 충돌 여부

### 15.2 확인 유효시간

- 생성·수정 확인 요청은 발급 후 5분 동안 유효하다.
- 만료된 요청은 실행하지 않고 새 요청을 시작하도록 안내한다.

### 15.3 1회 실행

- 확인 요청은 한 번만 실행할 수 있다.
- 동일 버튼 또는 요청이 재전송돼도 DB 변경은 한 번만 발생해야 한다.
- 실행 후 대기 명령 상태를 즉시 완료 처리한다.

### 15.4 재질문 대화 상태

- 누락 정보와 대상 선택을 기다리는 대화 상태는 마지막 상호작용 후 10분 동안 유지한다.
- 만료되면 저장된 후보를 폐기하고 처음부터 다시 요청하도록 안내한다.
- 사용자가 취소하면 즉시 폐기한다.

## 16. 카카오 챗봇 사용자 연결 규칙

1. MVP는 카카오 로그인에 의존하지 않는다.
2. 카카오 챗봇 스킬 요청에서 제공되는 봇별 사용자 식별값을 이용한다.
3. CalTalk 사용자 ID와 외부 식별값은 분리한다.
4. MVP 연결 관계는 한 CalTalk 사용자와 한 봇 사용자 식별값의 1:1 관계를 원칙으로 한다.
5. 이미 다른 사용자와 연결된 식별값은 자동으로 덮어쓰지 않는다.
6. 재연결이 필요하면 기존 연결을 해제한 후 새 코드를 발급한다.
7. 연결 코드는 짧은 만료시간, 1회 사용, 시도 횟수 제한을 적용한다.
8. 연결 해제 시 해당 식별값으로 일정에 접근할 수 없으며 기존 대기 명령도 무효화한다.
9. 연결되지 않은 사용자의 요청에는 일정 데이터를 반환하지 않고 연결 절차를 안내한다.
10. 외부 식별값 저장·보호 방식은 기술 설계서에서 확정한다.

## 18. 보안·개인정보 원칙

1. 모든 일정 조회·수정·삭제는 인증된 내부 사용자 ID를 기준으로 권한을 검증한다.
2. 클라이언트나 LLM이 전달한 사용자 ID를 권한 판단의 근거로 신뢰하지 않는다.
3. 비밀번호는 안전한 단방향 해시로 저장한다.
4. 연결 코드와 확인 토큰은 원문 장기 저장을 피하고 만료·1회 사용을 적용한다.
5. API 키, 비밀번호, 토큰, 운영 설정은 공개 저장소에 포함하지 않는다.
6. 일정 데이터와 사용자 입력을 로그에 무분별하게 기록하지 않는다.
7. LLM에는 명령 해석에 필요한 최소한의 텍스트만 전달한다.
8. 이메일, 내부 사용자 ID, 인증 토큰 등 명령 해석에 필요하지 않은 개인정보는 LLM 요청에서 제외한다.
9. 외부 서비스에 일정 텍스트가 전송된다는 점을 실제 공개 운영 전 개인정보 처리 안내에 반영한다.
10. 회원 탈퇴 시 본인 일정과 연결 정보를 삭제하거나 정책에 따라 비식별화한다.
11. 요청 횟수 제한과 연결 코드 시도 제한을 적용한다.
12. 변경 이력과 일반 애플리케이션 로그의 보관 범위는 기술 설계서에서 최소화 원칙으로 확정한다.

## 19. 장애 및 예외 처리

### 19.1 LLM 해석 실패

- DB를 변경하지 않는다.
- 지원 가능한 예시와 함께 다시 표현하도록 안내한다.
- 구조화 결과가 스키마를 통과하지 못하면 일반 오류가 아니라 재질문으로 처리한다.

### 19.2 LLM API 지연 또는 장애

- 제한 시간 안에 결과를 받지 못하면 해당 요청을 실행하지 않는다.
- 사용자는 재시도하거나 PWA에서 직접 일정을 관리할 수 있다.
- 실패한 비동기 작업이 나중에 임의로 일정을 변경해서는 안 된다.

### 19.3 카카오 연동 장애

- 카카오 요청은 실패 안내를 반환한다.
- PWA 직접 CRUD와 웹 대화 기능은 가능한 범위에서 계속 제공한다.
- 카카오 전용 오류가 공통 일정 서비스 전체 장애로 전파되지 않게 분리한다.

### 19.4 DB 또는 백엔드 장애

- 성공하지 않은 변경을 성공으로 안내하지 않는다.
- 재시도에 의해 중복 생성되지 않도록 요청 식별과 멱등성을 적용한다.

## 20. 카카오 기술검증 PoC

### 20.1 PoC 목적

본 개발 전에 카카오톡 채널 챗봇에서 CalTalk의 핵심 흐름을 실제로 구현할 수 있는지 확인한다.

### 20.2 성공 기준

1. 카카오비즈니스와 챗봇 관리자센터에 접근할 수 있다.
2. 카카오톡 채널과 테스트 봇을 생성하거나 연결할 수 있다.
3. 공중망 HTTPS 스킬 서버 URL을 등록할 수 있다.
4. 카카오의 HTTP POST 요청이 스킬 서버에 전달된다.
5. 요청에서 사용자 발화, 시간대, 봇별 사용자 식별값을 확인할 수 있다.
6. 스킬 서버가 카카오 규격의 JSON을 반환하고 실제 말풍선으로 표시된다.
7. 단순 조회 또는 고정 응답이 일반 스킬 제한 시간인 5초 안에 완료된다.
8. 일회용 코드로 PWA 사용자와 챗봇 사용자 식별값을 연결할 수 있다.
9. 연결된 사용자만 본인 일정에 접근할 수 있다.
10. 응답 지연 시 안전한 실패 안내를 반환할 수 있다.

### 20.3 콜백 대응

- MVP의 기본 경로는 일반 스킬의 5초 제한 안에 응답하는 것이다.
- 5초를 안정적으로 만족하지 못하면 AI 챗봇 콜백 기능의 신청 가능 여부를 별도 검증한다.
- 콜백 기능이 승인되지 않았거나 사용할 수 없으면 이를 MVP의 필수 전제로 두지 않는다.
- 콜백이 없어도 일정이 뒤늦게 자동 변경되는 구조는 사용하지 않는다.

### 20.4 중단 또는 범위 조정 기준

다음 중 하나가 해결되지 않으면 카카오 기능의 범위를 조정한다.

- 개인 개발 환경에서 채널·봇 생성 또는 배포가 불가능함
- 공중망 스킬 서버 연결이 불가능함
- 사용자 식별과 내부 계정 연결을 안전하게 구현할 수 없음
- 핵심 요청이 5초 제한을 지속적으로 초과하고 대체 경로도 사용할 수 없음

범위가 조정되더라도 PWA와 웹 자연어 일정 관리는 계속 개발한다.

## 23. 성공 기준

### 23.1 기능 기준

- PWA에서 본인 일정 조회·등록·수정·삭제가 가능하다.
- 웹 자연어로 특정 하루의 일정 조회·등록·수정이 가능하다.
- 카카오톡에서 특정 하루의 일정 조회·등록·수정이 가능하다.
- 챗봇 사용자 연결과 해제가 가능하다.
- 제목·날짜·시작 시간이 없으면 재질문한다.
- 종료 시간이 없으면 생성 일정에 한해 1시간을 설정한다.
- 수정 시 언급하지 않은 값과 기존 지속 시간을 올바르게 유지한다.
- 대상 일정이 여러 개면 사용자가 선택한다.
- 충돌 시 경고와 선택지를 제공한다.
- 생성·수정은 유효한 확인 후 한 번만 실행된다.
- PWA 일정 삭제가 정상 동작한다.

### 23.2 안전성 기준

- 다른 사용자 일정에 대한 접근 성공 0건
- 사용자 확인 없는 자연어 일정 생성·수정 0건
- 동일 확인 요청의 중복 실행 0건
- 만료된 확인 요청 실행 0건
- 연결 해제된 챗봇 사용자의 일정 접근 0건

## 28. 최종 MVP 정의

CalTalk MVP는 PWA를 독립적인 개인 캘린더로 완성한 뒤, 웹과 카카오톡 채널 챗봇에서 자연어로 특정 하루의 일정을 안전하게 조회·등록·수정할 수 있도록 하는 프로젝트다.

핵심 평가는 기능 수가 아니라 다음 세 가지로 판단한다.

1. 사용자의 말을 제한된 일정 명령으로 정확하게 구조화하는가
2. 모호함·충돌·중복 요청을 안전하게 통제하는가
3. 외부 채널과 LLM에 문제가 생겨도 사용자의 일정과 PWA 핵심 기능을 보호하는가
